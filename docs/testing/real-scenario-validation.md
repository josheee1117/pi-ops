# 真实业务与系统异常场景验收设计

状态：通知产品方向已批准，实施细节仍 proposed。尚未批准执行，所有场景尚未按本设计测试。

本设计先规定故障、证据和预期行为，再选择注入方式。测试不能用当前实现的输出反过来定义正确结果。目标是验证 Pi-Ops 能否正确发现故障、整理证据、决定是否叫人，并在故障恢复后闭环。

## 范围与依据

业务场景以真实 DataAsset 的接口、依赖、SQL 和关键任务为入口。系统场景覆盖 JVM、容器、健康状态和主机资源。Pi-Ops 自身的取证与模型故障单独验收。

设计依据包括以下文档：

- `test-infra/docs/adr/ADR-0002-dataasset-ai-ops-architecture.md` 的业务目标、通知策略和验收标准。
- `test-infra/docs/adr/ADR-0005-pi-ops-dual-source-and-node-agent.md` 的双事件源与只读边界。
- [PLAN-0002](../plans/PLAN-0002-architecture-consolidation.md) 的真实主机与 DataAsset 闭环优先级。
- [既有演练 Goal](../plans/GOAL-0001-local-fault-drills.md) 的隔离、证据与独立审查要求。
- [既有故障报告](../local-fault-drills.md) 的真实失败和能力缺口。

自写 Java Drill 可验证故障机制，但不能代替 DataAsset Starter、配置、事件转换与发送器的接入验收。本地制品 `data-asset-starter-0.0.1-SNAPSHOT.jar` 含发送器，但 `dev_jdk17` 的 `PiOpsTransportConfig.load` 默认关闭发送，公共部署描述没有 `PI_OPS_*`。未处理异常没有发送器发现路径。健康入口存在，应用没有安全制造 503 的开关。这些是绑定事实，不是开测批准。表中的业务入口仍不是 DataAsset 演练接口。旧 Java Drill 不是 DataAsset。首批绑定和离线合同见 [首批执行规格](first-batch-execution.md)。

本波允许应用 owner 在独立源码工作区补 DataAsset 与 Starter 的非预期请求异常事件源；中央只落文档，不修改生产通知逻辑、协议或治理门槛。不批准远端部署、故障注入、模型调用和外部通知。后续执行需要独立的目标与预算授权。

## 场景中的几个区别

- 预期业务拒绝是应用按业务规则拒绝请求，例如无权限、参数不合法或重复提交。它不自动等于运行故障。
- 非预期应用异常是代码未按约定处理的失败，例如请求返回 500 或任务异常终止。
- 故障是影响业务能力的实际问题。日志、JFR、Docker 和健康探测只是故障的不同信号。
- Incident 是对一个故障的记录。同一故障的多个信号需要关联，不能仅因来源或类型不同就分别叫人。
- 恢复需要正向成功证据。日志停止、负载注入结束或调查 COMPLETED 均不等于恢复。

## 已批准的通知产品方向

通知判断分成以下情况：

| 情况 | 预期行为 |
| --- | --- |
| 正常业务拒绝、普通单次 ERROR、短暂资源峰值 | 保存必要记录，不向群发送故障告警。 |
| CPU、GC、SQL 或依赖异常持续，但业务影响尚不明确 | 收证并分析。不能仅凭一个指标就确认故障或叫人。 |
| 确认服务不可用、关键任务失败、JVM OOME 或容器 OOM | 必须发送故障告警。模型失败不能取消确定性重大事故的通知。 |
| 同一故障持续，或出现更多关联信号 | 更新原 Incident，不重复发送首次故障告警。 |
| 有正向证据确认恢复 | 关闭该故障的活动状态。已发送故障告警的 Incident 发送一次恢复消息。 |

首次故障告警和恢复消息之外，调查完成消息默认只留作记录。重大事故先报已知事实，不能等待模型完成才报。普通异常需要分析后再决定是否发送首次告警。

用户已选方案一，无需重复批准此方向。[ADR-0030](../adr/ADR-0030-fault-notification-policy.md) 记录它与 ADR-0027 逐生命周期通知的差异；当前代码仍是旧策略。[最小实现规格](../plans/PLAN-0003-fault-notification-policy.md) 定义 proposed 的决定依据、顺序、离线断言和迁移边界。阈值与故障关联细节未绑定，不能视为全部合同已接受。告警计数按实际发送计，不用内部 NotificationJob 数量代替用户收到的消息数量。

## 业务异常矩阵

每一行包含正例和不该升级为故障的对照。具体阈值与窗口在执行前锁定，不能在失败后调低再沿用原评分。

| ID | 实际场景与对照 | 发现入口与最小证据 | 允许的诊断与通知预期 | 恢复证据 |
| --- | --- | --- | --- | --- |
| B01 | 同一接口的合法成功请求，以及预期的参数、权限或重复提交拒绝。不得仅修改日志文本模拟业务状态。 | 实际请求、接口约定、响应状态、业务错误码和 traceId。核对 Starter 是否把预期拒绝错误升级。 | 识别为预期业务结果，不推测库存或依赖故障。无故障告警。 | 不建立故障时不发送 RECOVERED。后续合法请求成功只是对照。 |
| B02 | 普通请求发生真实未处理异常。分别测试单次异常和同一抛出点的持续失败。对照为同接口成功请求。 | Starter 或应用事件、实际异常类与栈、请求状态、失败次数与总请求数。health 保持正常，不能用健康失败替代业务发现。 | 确认应用异常和可见抛出位置。只有源码或调用证据支持时才归因到具体分支。单次普通异常记录，持续且确认影响业务时告警。 | 同接口与同业务操作恢复成功，并通过预先规定的恢复观察窗。 |
| B03 | 已绑定的实际依赖出现超时、连接拒绝或错误响应。每次只改变一种条件。对照为一次可恢复超时和正常依赖响应。 | 调用方的目标与操作、超时配置、实际耗时、traceId、异常及受控依赖侧记录。独立健康 GET 不等于业务调用成功。 | 区分依赖响应慢、连接失败与调用方处理异常。不能只凭异常文本确定是 DNS、网络或依赖内部错误。持续业务失败时告警。 | 同一路径的实际依赖调用与业务请求成功。另一健康接口返回 200 不够。 |
| B04 | 真实 SQL 变慢。分别测试锁等待和查询执行慢，不混合注入。对照为单次 1 至 2 秒 SQL 和正常查询。 | Starter 慢 SQL 事件、statementId 或 digest、耗时、请求影响。锁等待与执行计划归因还需要真实数据库只读证据。参数脱敏。 | 可以确认慢 SQL。没有锁、计划或 digest 统计时不能断言缺索引或锁竞争。偶发记录，持续恶化后分析，确认影响业务时告警。 | 同 digest 的延迟和业务请求恢复正常。解除注入不直接算恢复。 |
| B05 | 真实关键异步任务或批处理失败，HTTP health 仍正常。对照为业务允许跳过的记录或可成功重试的普通任务。 | 真实任务类型、执行 ID、失败阶段、异常、结果和对业务的影响。执行前确认该任务确实关键。 | 确认任务失败，不把全站 health 正常当作业务正常。关键失败必须告警，预期跳过不告警。 | 同类任务经授权重跑成功，且结果得到核对。禁止自动重跑有副作用的业务任务。 |

B02 和 B05 还要各验证一次两个独立业务操作同时失败。若错误码或日志相似但故障对象不同，不应错误合并。

## 系统异常矩阵

| ID | 实际场景与对照 | 发现入口与最小证据 | 允许的诊断与通知预期 | 恢复证据 |
| --- | --- | --- | --- | --- |
| S01 | JVM 持续 CPU 压力。对照为短时忙循环和低于阈值的实际样本。 | 真实应用检测或黑盒检测事件、持续时间、Docker CPU 区间和容器配额。热点归因需要执行采样或线程证据。 | 区分机器 CPU 归一化与容器配额占用。没有采样时不能定位热点方法或排除 GC。短峰值不告警，持续压力先分析业务影响。 | 实际 CPU 降至恢复阈值，业务请求成功，并通过恢复窗。 |
| S02 | 堆高水位或 GC 压力，但没有 OOME。对照为短时分配后 GC 回收、业务正常。 | 实际堆占用、GC 时间或停顿、持续窗口和业务延迟。没有这些字段时不能用 Docker RSS 替代。 | 区分可恢复堆压力和 JVM OOM。不能仅凭一次高占用判定内存泄漏。确认影响业务时告警。 | 堆与 GC 指标回到恢复条件，业务能力正常。 |
| S03 | 真实 JVM 堆 OOME，容器可以继续运行。对照为 S02 的可回收高水位。 | 真实 OOME 类、文本与栈、堆配置、事件时间、Docker 状态。 | 确认 JVM 堆 OOM，必须告警。不得误称容器 OOM kill，也不得用 JFR 观测事件名作为分配热点。 | 后续相关业务操作成功，且恢复窗内没有同类失败。容器 Running 和 health 200 单独不足以证明恢复。 |
| S04 | 容器达到 cgroup 内存限制后被 OOM kill。对照为受控外部 SIGKILL。 | Docker raw oom、die、OOMKilled、退出码、实际内存限额和主机内存。模型只能看到按权限取得的证据。 | 把同次 oom 与 die 关联为一个故障，发送一次首次告警。退出码 137 单独不能证明 OOM。 | 经授权启动后的服务身份、实际就绪状态和业务请求成功。新容器需关联到原故障，不能借无关服务的健康状态闭环。 |
| S05 | 进程非零退出。对照为正常 exit 0、计划内重启和正常启动。 | Docker 原始事件、实际退出码、退出前日志、状态和维护事实。 | 确认进程退出，原因未知时保留未知。正常维护不误报，start 不自动等于故障 restart。异常退出影响可用性时告警。 | 服务恢复就绪并可服务请求。单个 start 事件不足以证明恢复。 |
| S06 | 配置的健康接口持续 503 或不可达，再恢复。对照为一次瞬态失败。 | 实际 HTTP 探测结果、连续失败窗口、容器状态和必要日志。 | 确认配置目标不可用，持续失败必须告警。不能仅凭 503 判定数据库故障。持续失败不重复建单。 | 同目标连续成功，原 Incident 恢复，一次恢复消息。 |
| S07 | 主机内存压力或磁盘压力。两者分别测试。对照为低于阈值与短暂峰值。 | 对应主机的真实指标、阈值、持续时间。磁盘需确认路径与文件系统，内存需区分容器限额和主机可用量。 | 分配给主机诊断，不落入业务异常。不能只凭 load 或单个容器指标断言主机资源耗尽。确认持续影响时告警。 | 同一主机或文件系统回到恢复条件，并通过恢复窗。 |

S07 只能在另行批准的一次性虚拟机或隔离环境执行。禁止在共享宿主机耗尽内存或写满磁盘。模拟指标可验证规则，但不能替代主机真实故障验收。

JVM 死锁与连接池耗尽作为后续扩展。先确认对应的实际检测和证据入口，再设计单独案例，不用 CPU 或慢 SQL 案例宣称已覆盖。

## Pi-Ops 自身失败矩阵

| ID | 条件 | 预期行为 |
| --- | --- | --- |
| F01 | 故障事件已入库，Node 在收证时不可达，之后恢复。 | 失败证据明确为传输或取证失败，不伪造目标不健康。区分已有必要事实与缺失的补充。恢复后能够继续或通过明确操作重试，同次故障不重复叫人。预算耗尽的终态和恢复入口都要验收。 |
| F02 | 模型超时、Runtime 在 ACK 后崩溃、结果回调短时失败。每个条件独立执行。 | Event、Incident 和 Evidence 保持可用。确定性重大事故仍通知真实事实。调查与投递各自遵守重试上限，失败不能标成准确诊断。恢复后回调不重复写结果或发送首次告警。 |
| F03 | 故障关键日志位于第 20 行之后，或合法异常栈超过中央上下文单项预算。 | 对照 raw Evidence 与实际模型上下文。模型可见信息不足时必须保留缺失或截断说明，不能声称完整日志。不得只提高 Runtime 预算就宣称中央裁切问题已解决。 |

## 每个场景开测前必须绑定的内容

同一场景的执行记录包含以下字段。缺少目标、预期或安全边界时不执行。

| 内容 | 必须填写的值 |
| --- | --- |
| 真实入口 | 应用与镜像版本、Starter 版本、接口或任务、容器、nodeId、实际事件类型与字段。 |
| 业务影响 | 成功请求数、失败请求数、总请求数、延迟或任务失败结果。不能只有一行 ERROR。 |
| 测试参数 | 触发阈值 T、触发窗 W、恢复阈值与恢复窗 R、采样间隔、调用超时。必须写具体值及配置来源。 |
| 负载与持续时间 | 正例和对照各自的请求数、速率、资源限额、注入持续时间和停止时限。 |
| 预期结果 | 是否建 Incident、哪些信号属于同一故障、必要 Evidence、可接受诊断、首次告警数和恢复消息数。 |
| 当前缺口 | 缺检测器、缺适配器、缺事件映射或缺恢复语义。不能为了通过临时添加另一种无关故障。 |
| 执行预算 | 实际 run 数、最大模型调用数、最大外部消息数，以及允许的重跑次数。由执行批次单独确认。 |

以正常运行 60 秒作为初始基线。若实际触发窗或恢复窗更长，基线至少覆盖较长窗口。持续异常正例完整覆盖 W。瞬态对照短于 W。恢复观察完整覆盖 R，不能因等到了 COMPLETED 提前结束。

阈值以已批准的实际配置为准。没有产品阈值时先确认策略，不由执行者边测边定。为本地复现单独校准的结果必须标明，不能当成产品默认配置通过。

每种故障都有独立的真实原因记录。服务名、错误消息和模型输入不得附加预期答案。真实异常栈、状态码和业务错误码可以作为证据。注入动作记录、源码核对和故障设置供事后审查使用，不直接发送给 Runtime。

## 判定方式

每个实际 run 分别评定以下阶段：

| 阶段 | 验收条件 |
| --- | --- |
| 发现 | 正例在 W 与已声明的传输预算内产生预期信号。对照不产生故障告警。同一故障多源信号关联，独立故障不误合并。 |
| 收证 | 必要证据与故障对象、发生时间相符。失败、缺失和裁切可见。raw 事实与模型上下文不混为一谈。 |
| 诊断 | 主张有当前成功 Evidence 支持。故障分类正确，或在缺证时明确不能确定。不得把分类正确当成具体根因已定位。 |
| 通知 | 实际发送符合已确认策略和数量。区分内部任务、平台接受与人类可见。DELIVERED 单独不证明群身份或群内可见。 |
| 恢复 | 正向证据满足 R。Incident 状态和已通知故障的恢复消息一致。没有通知过的普通记录不凭空发送恢复告警。 |

结果使用 PASS、FAIL、GAP、BLOCKED 和 NOT_RUN。它们表示本次实际检查的结果，不表示整个产品成熟度。前提缺失记 BLOCKED，能力未实现记 GAP，实际结果不符合预期记 FAIL。未调用的模型和未发送的消息记 NOT_RUN。

COMPLETED 只表示调查执行完成。补证专员失败、空引用、事实不足或业务归因错误都要单独记录。事后审查对照独立原因记录与模型实际可见证据，不能要求模型猜出没有收到的深层原因。

## 执行顺序

1. 先绑定真实 DataAsset 的 Starter、发送器和业务入口。B01、B02 和 S06 先验证不误报、确实能叫人以及恢复闭环。此批失败时不扩大场景。
2. 再执行 B03、B04、S01、S02、S03 和 S04，验证依赖、SQL、CPU、GC 与两种 OOM 的区分。缺数据库或 JVM 证据入口的案例保持 GAP，不用通用建议补成 PASS。
3. 最后扩展 B05、S05、S07 与 F01 至 F03，验证关键任务、维护对照、主机资源和系统自身失败。F03 的离线上下文核对可以在第一批执行前完成。

初次执行每个选中场景的一组正例和对照。关键正例通过后，再按批准预算独立重复一次。失败后先核对根因，只允许批准范围内的有界修正与重跑。旧报告和失败证据不重评分、不覆盖。

本设计不授权一次跑完全部矩阵。每批完成都保留原始证据，再决定是否进入下一批。复用现有部署与演练代码，不先建设通用故障注入平台。

## 安全与开测条件

- 本机先验证故障机制。真实 DataAsset 的受控故障和测试主机操作需要 owner 单独批准，不沿用旧本地演练的授权。
- 白盒正例必须通过真实应用发送器。禁止手工 POST 伪造事件作为应用接入证明。黑盒正例关闭应用发送器，不用额外健康故障掩盖发现能力缺失。
- 每次只改变一个故障条件。SQL、任务和业务数据使用测试数据，事先核对副作用与清理范围。禁止删除真实数据或自动重试写业务请求。
- 发通知前核对已批准测试目标的 URL 摘要、实际容器配置和新队列。不得打印 webhook、token、完整 Env 或模型凭证，不回放历史任务。
- 外部通知先经本地接收器核对格式与数量。接收器不能替代真实企业微信交付验收。真实交付只在另行批准的测试群和消息预算内执行。
- 使用独立 run ID 与数据库，保留故障前、故障中和恢复后的记录。停止故障负载与观察器后保留证据，不清空历史数据。

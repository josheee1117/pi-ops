# ADR-0030：按故障影响决定通知

状态：accepted。2026-10-21 用户确认通知规则。步骤 4 和 5 实现中央事实转换、决定与持久排程；真实部署、真实模型效果和企微投递仍单独验收。

## 决定

1. JVM 堆 OOM、容器 OOM kill、Docker 日志还原的真实 OOME、栈溢出和已绑定健康目标不可用必须通知，不等待模型。关键接口及核心业务流程的核心接口报错同样通知。中央按服务配置路径或操作名、业务流程和可选负责人，不靠异常文本猜关键性。
2. 持续报错但影响未知时先收证分析。服务配置等待期和最大观测间隔。到期仍有持续观测时发一次"需要人工确认"。模型失败不延后期限。预期 4xx 拒绝、瞬态异常、单独 exit 137 不授权告警。
3. 完成调查本身不通知。首次通知交付后，只有结构化修复动作或绑定事实带来新影响时补发一次"诊断更新"。重复报告、置信度变化、只有补证建议均不补发。恢复后到达的报告只保存。恢复前尚未交付的诊断更新终止为 FAILED，并写明 suppressed 原因。
4. 已决定首次告警但尚未发送就恢复，保留首次任务，写成"曾发生、现已恢复"。这条消息已经表达恢复，不另发恢复消息。发送中才恢复时无法撤回网络请求，确认首次交付后排一次恢复。首次最终 FAILED 不发孤立恢复。

这取代 [ADR-0027](ADR-0027-durable-operational-notification-delivery.md) 的逐生命周期无差别排程。Pi-Ops 拥有事实、决定和投递，Runtime 只提供分析。模型自由文本、COMPLETED 状态和置信度都不是影响事实。

## 实现边界

`EventStore.evaluateNotification()` 是新策略的唯一决定与排程入口。SQLite 事务保存决定、任务和首次交付后的恢复联动。创建、追加、新证据、调查完成或失败、等待期轮询、恢复和首次交付都触发它。决定失败用 savepoint 隔离，只记录可见错误，不回滚其他事件的合法接收。

复用 Incident、任务 ID、唯一索引、状态 guard 和有限重试。通知 worker 即使没有 webhook 也执行期限判断，但不伪造 DELIVERED。外部交付仍是至少一次，发送成功后确认前崩溃可能物理重发。

迁移只新增列、表和索引。旧 Incident 与任务标记 legacy，不回填新决定，不取消、重排或改写旧队列。旧记录的新事件在原聚合窗内继续归入旧记录，不因升级重新通知。旧指纹版本保持原语义。新策略把操作及健康目标身份纳入指纹，已明确身份的活跃故障跨聚合窗口复用，正向恢复后再次失败创建新故障。

配置、默认值、验证和已知生产者缺口见 [PLAN-0003](../plans/PLAN-0003-fault-notification-policy.md)。本决定不授权部署、真实故障注入、真实模型调用或外发。

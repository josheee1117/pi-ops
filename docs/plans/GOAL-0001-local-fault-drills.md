# 本地 Java17 与 Docker 故障演练 Goal 提示词

将以下内容作为执行模型的目标。先在本地完成，不向测试机器部署。

## 目标

用真实故障回答：Pi-Ops 能否发现 Java17 应用和 Docker 工作负载的问题，收集事件与日志，给出有证据的诊断，并向已配置的企业微信群发送通知？交付可重跑的演练代码和逐项事实报告。不要把链路畅通当作诊断正确，也不要把 demo 成功当作真实 DataAsset 已通过验收。

遵守 `CONTRIBUTING.md`。以 `docs/plans/PLAN-0001-dual-source-v0.1-implementation.md` 和 `docs/plans/PLAN-0002-architecture-consolidation.md` 为产品范围依据。复用 `deploy/local/jdk17-drill/`、现有 Compose 和 smoke，不另外搭一套产品。

## 验证两种观测方式

白盒使用 Java17 `RecordingStream` 读取实际产生的 JFR 事件，再通过应用发送器提交 EventBatch。业务异常可以使用真实提交、真实消费的自定义 JFR 事件。保留原始 JFR 名称、时间、异常类或采样值，以及应用日志。不得让演练脚本直接伪造 JFR 事件投递到 Pi-Ops。

黑盒关闭应用发送器，验证 Node Agent 的 Docker、主机和健康探测。故障仍由 Java 应用或容器实际产生。不得手工提交事件，不得为了让不可观测的错误被发现而额外切换健康状态。若设计中的监控方式看不到某类问题，记为能力缺口。

区分 JVM 堆内存耗尽与容器内存耗尽。前者应产生真实 `OutOfMemoryError`，可以在释放演练内存后保持 JVM 存活。后者必须用 Docker `oom` 事件、退出状态和 `OOMKilled` 等可取得的证据证明，不能把任意退出码 137 当作 OOM。

## 演练范围

逐项执行以下场景。先跑一次完整矩阵，再重复实际可观察的核心正例一次，检查结果是否可重现。对已证实缺少探测器的场景，不反复等待同一种超时。

| 编号 | 通道 | 实际故障 | 判定重点 |
| --- | --- | --- | --- |
| W1 | 白盒 | 有时限的 CPU 忙循环 | 实际 `jdk.CPULoad`，CPU Incident，采样证据和有引用的诊断 |
| W2 | 白盒 | JVM 堆 OOM | 真实 OOME、JFR 和日志，诊断不得误称容器 OOMKilled |
| W3 | 白盒 | 请求处理业务异常 | 真实异常、自定义 JFR 和日志，健康接口保持正常 |
| B1 | 黑盒 | CPU 忙循环，发送器关闭 | Docker 或主机监控是否主动发现；仅能按需采集 CPU 不算发现 |
| B2 | 黑盒 | 容器 cgroup OOM | Docker OOM 事实、Incident、有限证据、诊断和通知 |
| B3 | 黑盒 | Java 进程非零退出 | Docker die、退出码及日志；不得臆断为 OOM |
| B4 | 黑盒 | 健康接口 503 后恢复 | OPEN、诊断、RECOVERED，持续失败不重复建 Incident 或重复通知 |
| B5 | 黑盒 | 仅业务错误日志，健康仍为 200 | 是否存在实际日志发现通道；没有则说明不能主动发现 |
| N1 | 两通道 | 无故障基线 | 在完整探测窗口内没有新的故障 Incident |
| N2 | 白盒 | 低于阈值的实际 CPU 样本 | 不触发 CPU 压力事件；不得只关闭整个探测器 |
| N3 | 黑盒 | 正常退出或重启演练容器 | 按现有策略判定，不将无故障维护算成业务故障 |
| F1 | 收证 | Node Agent 在真实收证阶段不可用 | 返回可重试失败，不伪造健康失败；恢复后能够收证 |

不要扩成所有故障类型的测试平台。以上场景发现的新问题，只修直接阻塞本次验收的根因。CPU 或业务日志等缺少完整主动探测设计的能力，先记录最小后续方案，不趁演练引入通用插件或任意 shell 执行。

## 诊断必须接受事实检查

将注入动作、预期根因和容器资源配置保存在独立的 ground truth 文件。不要把这份文件送给 Pi Runtime。服务名、Incident message 和模型输入不得包含“人为注入 CPU”“这是业务异常演练”等答案提示。原始 JFR 事件类型、异常栈、退出码和实际业务错误内容是可使用的证据。

每个场景分别检查发现、收证、诊断、通知和恢复。诊断通过至少满足以下条件：

- 引用的 Evidence ID 存在，属于当前 Incident，证据状态和内容支持对应主张。
- 能区分 JVM CPU 压力、JVM 堆 OOM、容器 OOM、应用异常与健康失败，或明确说明当前证据不能确定根因。
- 没有把未取得的日志、线程栈、Docker 状态或指标当作已观察事实。
- 建议与证据相关，不要求 Pi-Ops 自动执行修复。

由独立、只读审查者在报告生成后对照 ground truth 评分。对“无法确定”保留不确定性，不强行判成准确诊断。记录原文和具体不符之处，不只给一个总分。

## 保存可复核的证据

每次执行使用独立 run ID 和 SQLite 数据目录，保留失败的运行。每个场景至少记录以下内容：

- 提交版本、实际执行命令、JDK 与 Docker 版本、资源限额、探测阈值和超时配置。
- 故障注入时间、实际 JFR 与应用日志、Docker 事件和状态等原始事实。
- Event ID、source、producer、时间与类型，Incident ID、状态和事件数量。
- Evidence ID、kind、status，以及原始视图与模型可见视图中的必要片段。
- 实际模型 provider、model、REAL 模式、Session 状态、耗时、报告原文和引用。
- 通知类型、次数、重试次数与企业微信响应。`DELIVERED` 与企业微信 `errcode=0` 证明平台接受，不证明人已在群里看到。
- 各阶段结果，使用 `PASS`、`FAIL`、`GAP`、`BLOCKED` 或 `NOT_RUN`，并写明依据。

将机器结果和原始记录放在 Git 忽略的 `artifacts/` 或 `deploy/local/data/`。提交最小演练代码和不含秘密的事实报告。报告注明完整证据目录。不能取得的证据写缺失，不能用 stub、上一轮记录或主观阅读填充。

## 执行边界

- 只对命名明确的本地一次性 demo 容器注入故障。限制 CPU 持续时间和内存使用，容器设置 CPU 与内存限额。不要对宿主机、真实 DataAsset 或无关容器注入故障。
- 产品只观察和诊断。故障注入属于开发演练代码，不增加产品远程执行、容器控制或自动修复能力。
- 用 Git 忽略的 `deploy/local/.env.jdk17` 中现有企业微信配置。不得把 webhook、API key 或 bearer token 放进 Goal、委派参数、Git 或报告。
- 通知标明本地演练和 run ID，不标明预期根因。串行运行故障，控制发送速率，避免重放历史 Docker 事件或无关容器变更刷群。
- 模型必须真实调用，不允许 fake 结果替代。真实 API 不可用时保存失败证据并报告。不得为通过测试忽略失败或无限重试。
- 先记录默认配置的表现。若模型需要超过默认执行时限，另记显式放宽配置的结果，不能把放宽后的成功称作默认配置通过。
- 不删除旧证据，不重置治理门槛，不重新标注 Proof grade，不部署远端，不推送或合并未经治理验收的修改。
- 结束或失败时停止观察器，恢复健康开关，停止故障负载。保留报告和数据库供复核。

## 与子代理分工

主会话负责目标、边界、结果复核和用户汇报。并行工作必须隔离写入目录或 worktree。

1. 一个实现子代理只扩展 Java17 demo 的实际 JFR 与故障模式，保留运行验证和组件交接。
2. 一个只读子代理核对黑盒探测、事件映射、JFR 语义、证据收集与恢复规则，给出可执行矩阵和已知缺口。
3. 在前两项交接完成后，由一个集成执行者接入 Compose 和最小演练脚本，串行运行实际场景。集成执行者是唯一操作共享 Docker 和企业微信的代理。
4. 在实际结果完成后，由新上下文的只读审查者检查证据与诊断。确认问题才做一次有界修正和重跑，保留修正前结果。

子代理基础设施失败时停止对应流程，报告 run、cwd、worktree、branch、ref 和已产生的 diff。不得静默切换到其他 CLI 或前台执行模式。

## 完成条件

完整矩阵有结果，关键正例已重复验证，所有通过项都有实际故障及下游证据，所有缺口和阻塞都明确列出。类型检查、构建、相关单元测试及演练检查真实运行通过，独立审查未留下未说明的结论错误。

允许交付“尚不可转测”的结论。最终报告回答已验证的能力、没覆盖的能力、已修复的问题和下一步优先级。真实 DataAsset、两台测试机器、不同架构和长时间稳定性若未测，必须继续列为未验证。

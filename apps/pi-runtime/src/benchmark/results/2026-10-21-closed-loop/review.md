# 闭环评测第一批结果（2026-10-21）

## 结论

7 个固定案例各跑一次，7 例的处理方案全部通过预设标准，判定闭环 7/7。没有出现详情取不到、诊断未生成或处理 agent 无结论的案例。用真实诊断链路生成消息，用真实 HTTP 详情接口下发诊断，没有发送企微。

这个 7/7 说明的是：**消息 + 详情接口 + 已提供的源码夹具，足以让一个胜任的 agent 给出符合预设标准的处理方案。** 它不等于 7 个故障都被修好了。4 个没有源码夹具的案例，预设标准本身就要求“先补证据/取源码再修”，所以闭环表示方案可执行，不表示修复代码已经确定。

每条消息 778 至 922 字节，都是人话摘要加详情地址。7 个处理 agent 都先按消息里的地址取详情，没有一例绕过详情接口直接作答。3 个有源码夹具的案例多花一轮读源码。

裁判的 6 个处理项和 2 个归因项在 7 例全部通过。归因项通过意味着这批诊断的根因和已知事实没有冲突：DataAsset 定位到注入端点，OOM 区分了 JVM 堆和容器内存，CPU 明确写了机器归一化不是配额利用率，栈溢出没有误判成堆 OOM。

## 与上次评测的差别

`results/2026-10-21-output-budget/review.md` 记录的诊断内容问题，本批没有复现：DataAsset 的 NanoCpus 写成了 2000000000，OOM 没有把 docker.stats 当堆使用，CPU 写清了归一化口径。这是单次运行的内容差异，不是新修复。不能据此说内容质量已经稳定，仍需多次运行观察。

## 首轮冒烟暴露的问题

正式 7 例之前跑过两次单例冒烟，它们暴露了两个问题；正式 7 例在修正后的装置上跑完：

1. 首版处理循环只接受 `{"tool":"answer"}`。真实模型给了一次不带 `tool`、直接带 `rootCause` 与 `actions` 的结论，被连续判成未知工具，案例记为未闭环。证据：`artifacts/closed-loop-smoke/dataasset-197.json` 的 `handler.error` 为“处理 agent 连续使用未知工具：undefined”。修正后接受不带 `tool` 的结论。
2. 同一次冒烟的真实诊断走了降级路径，消息写明“诊断不完整，先按建议止损并获取详情”，但自动检查仍算通过。证据：`artifacts/closed-loop-smoke/report.md` 第 26 行。下一次同一个案例生成了完整诊断。说明降级路径仍可能被真实模型触发，闭环率会受诊断稳定性影响。

这两条都是本机临时产物，在 `artifacts/` 下，不进仓库。

## 标准与裁判的边界

- 判定标签由裁判的逐项结果按固定规则推出，不采用裁判自由总评。6 项全过为闭环，案例声明的 critical 项失败为未闭环，其余为部分闭环。
- 裁判是模型，只证明“按这份标准，方案成立”。它放过了两处超出标准的断言：CPU 案例写“业务并未发生故障”，OOM 案例写“该实例是演练实例”。当时的预设标准没有禁止这两句，所以没有判失败。要更严，应在下一版预设标准里明确写出。
- 4 个无源码案例的闭环依赖“先补证据/取源码”这一允许修复方向。它代表方案正确，不代表问题已经解决。
- 处理 agent 是本评测的无状态 JSON 工具循环，每轮重发详情。CPU 案例详情 19KB、3 轮，单例 72032 token，大部分花在重复上下文。换成有会话记忆的实现会降低成本，也可能改变闭环率。
